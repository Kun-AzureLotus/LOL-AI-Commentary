# 技术栈

## 技术选型原则

当前阶段不应过早锁死所有实现细节。技术栈应优先支持以下目标：

- 实时性。
- 合法信息边界。
- 本地优先。
- 可替换的 AI、视觉和语音组件。
- 长期开放源项目的可维护性。

MVP 应优先验证端到端体验，而不是追求完整平台化能力。回放系统和审计日志系统保留到后续阶段。

## 桌面应用

推荐方向：

- Windows 优先。
- 桌面端负责运行本地采集、状态处理、解说生成和语音输出。
- UI 在 MVP 中保持最小化，重点是配置、状态显示和调试信息。

候选技术：

- Tauri：适合本地优先桌面应用，资源占用较低，便于分离前端 UI 与本地后端能力。
- Electron：生态成熟，但资源占用更高。
- 原生桌面框架：性能和系统集成能力强，但开发成本更高。

建议：

MVP 可以优先考虑 Tauri 或其他轻量桌面方案，但在技术验证完成前，不应把架构绑定到某个 UI 框架。核心领域模块应独立于桌面框架。

## Riot 实时客户端 API

用途：

- 获取结构化游戏事实。
- 作为击杀、目标、玩家状态和游戏时间等信息的主要来源。

技术要求：

- 本地 HTTPS 客户端。
- 超时、重试和连接状态管理。
- API 响应标准化。
- 版本变化兼容策略。

建议：

将 Riot API 封装为独立 Adapter。Adapter 只输出标准化数据，不做解说判断。

## OBS 屏幕捕获

用途：

- 获取 API 无法提供的视觉上下文。
- 识别玩家当前画面、小地图、技能动画、团战视觉效果和镜头位置。

候选方式：

- OBS 插件或 WebSocket 集成。
- 本地屏幕捕获。
- 视频帧流读取。

建议：

MVP 应先选择稳定、可调试、低侵入的 OBS 集成方式。视觉识别结果必须带置信度和时间戳，不能直接作为确定事实进入解说。

## 视觉解析

用途：

- 小地图动向识别。
- 技能动画和视觉特效识别。
- 玩家视角和镜头焦点判断。

候选技术：

- 传统计算机视觉，用于 UI 区域裁剪、颜色/模板识别、运动检测。
- 轻量本地视觉模型，用于较复杂的画面理解。
- 多模态模型，用于较高层画面摘要。

建议：

MVP 不应依赖大型多模态模型直接理解全画面。更稳妥的路线是先做受限视觉任务，例如小地图区域裁剪、可见单位变化、技能特效候选检测，再与 API 数据融合。

## 状态处理

用途：

- 维护当前比赛状态。
- 合并 API 与视觉输入。
- 识别事件。
- 解释事件意义。

建议技术方向：

- 使用强类型领域模型描述比赛状态、事件、置信度和来源。
- Event Detection 与 Game State Engine 分离。
- 核心状态逻辑应独立于 UI、LLM 和 TTS。

关键设计：

- 所有状态带时间戳。
- 所有视觉事实带置信度。
- 所有可解说事实带来源。
- 过期状态必须被丢弃或降级。

## Narrative Director

用途：

- 决定是否发言。
- 决定发言优先级。
- 决定情绪强度和解说风格。

实现方向：

- MVP 可先使用规则引擎和评分模型。
- 后续可以引入更复杂的策略模型，但必须保持可解释。

建议：

Narrative Director 不应直接由 LLM 承担。它是系统控制层，应尽量结构化、可测试、可审计。

## Prompt Builder

用途：

- 将叙事决策和状态摘要转换为结构化 LLM 提示词。
- 限制 LLM 的事实来源和输出边界。

技术要求：

- 模板化提示词。
- 明确的事实白名单。
- 明确的禁止输出规则。
- 输出长度和风格控制。

建议：

Prompt Builder 应是 LLM 的唯一输入入口。任何模块都不应绕过 Prompt Builder 直接调用 LLM。

## LLM

用途：

- 将结构化提示词转成自然语言解说。
- 提供专业电竞解说风格。

候选方案：

- 云端 OpenAI-compatible API。
- 本地小模型。
- 混合模式：本地规则决策，云端生成表达。

建议：

MVP 可以支持 OpenAI-compatible API 以降低验证成本，但架构必须保留 provider 抽象。长期应评估本地模型，以降低隐私和延迟风险。

LLM 不应承担以下职责：

- 读取原始 API 数据。
- 读取原始画面。
- 判断隐藏信息。
- 做操作建议。
- 决定是否发言。

## TTS

用途：

- 将解说文本转为实时语音。

候选方案：

- 云端 TTS。
- 本地 TTS。
- 游戏解说风格定制音色。

技术要求：

- 低延迟。
- 可打断。
- 可丢弃过期语音。
- 可配置语速、音量和音色。

建议：

MVP 应优先验证延迟和可听性。解说文本如果在事件发生数秒后才播放，可能应被丢弃，而不是继续排队播放。

## 本地存储

用途：

- 保存用户设置。
- 保存模型和 TTS 配置。
- 保存少量运行状态。

候选方案：

- SQLite。
- 本地 JSON 配置。

建议：

MVP 可以从简单配置开始。SQLite 更适合后续扩展到历史配置、解说偏好和调试数据。回放与审计日志不属于 MVP，但未来可能需要更系统的本地数据模型。

## 测试与验证

MVP 阶段应优先验证：

- Riot API 采集是否稳定。
- OBS 捕获延迟是否可接受。
- 小地图和视觉识别是否足够可靠。
- Event Detection 是否能准确识别基础事件。
- Game State Engine 是否能解释事件重要性。
- Narrative Director 是否能减少噪音。
- Prompt Builder 是否能防止 LLM 越界。
- TTS 是否能在合理时间内播放。

## 后续阶段能力

以下能力重要，但不纳入 MVP 必须项：

- 回放系统。
- 审计日志系统。
- 大规模自动化评测。
- 多语言解说。
- 自定义解说员人格。
- 主播专用混音和 OBS 场景联动。
- 本地模型完整离线模式。
