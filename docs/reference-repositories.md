# 参考代码库借鉴

## 原则

以下仓库仅用于学习架构和工程设计思路。我们不会复制其代码，也不会照搬其产品方向。

每个参考项目都应从三个角度评估：

- 有什么值得学习的理念。
- 该理念的局限性是什么。
- 我们应采纳、改进还是放弃。

## Masmedeam/leagueofcommentary

仓库地址：

https://github.com/Masmedeam/leagueofcommentary

### 有用理念：原始数据与简化数据分离

用途：

该项目会抓取 Riot 数据，并保存原始比赛数据和简化后的摘要。这种思路有利于调试、复盘和理解数据处理过程。

局限性：

它更接近赛后或历史比赛素材处理，不是实时解说系统。它没有 OBS 视觉输入，也没有合法可见性过滤。它的回放和媒体播放思路不属于我们的 MVP。

建议：

采纳“原始输入与下游摘要分离”的理念，但把回放能力放到后续阶段。MVP 不应为回放系统付出复杂度。

### 有用理念：覆盖层与音频播放原型

用途：

该项目展示了桌面覆盖层和音频播放可以组合成赛事化体验。

局限性：

覆盖层不是我们的核心输出方式。我们的当前目标是语音解说，不是视觉面板。参考项目的实现也不适合直接迁移。

建议：

只保留“语音和视觉素材可以形成赛事氛围”的产品启发，不采纳具体实现。

## Giggitycountless/LOL-AI-Intelligence

仓库地址：

https://github.com/Giggitycountless/LOL-AI-Intelligence

### 有用理念：桌面端分层架构

用途：

该项目使用清晰的分层思路，将领域模型、应用逻辑、适配器、存储、平台边界和前端分开。这对长期开放源项目非常有价值。

局限性：

它的产品目标是桌面助手和 AI 教练，包含自动接受、自动选人、自动符文、聊天预设和战绩侦察等能力。这些能力与我们的产品边界冲突。

建议：

采纳分层架构理念，放弃其教练、自动化和侦察功能方向。我们的领域模型应围绕合法可见事实、事件、游戏状态、叙事决策和语音解说。

### 有用理念：本地优先

用途：

本地存储、本地配置和用户自管 API key 有利于隐私和开源信任。

局限性：

如果使用云端 LLM 或 TTS，本地优先仍然不等于完全隐私。必须明确哪些数据会离开本机。

建议：

采纳并加强。MVP 可以支持云端 provider，但应最小化上传内容，并为长期本地模型和本地 TTS 留出架构空间。

### 有用理念：Live Mode

用途：

该项目区分桌面模式和游戏中模式。我们的系统也需要根据游戏阶段和当前上下文调整行为。

局限性：

参考项目的 Live Mode 偏向数据展示和辅助决策，容易形成竞技优势。我们的 Live Mode 不应成为信息面板或教练入口。

建议：

改进采纳。我们的 Live Mode 应驱动解说节奏、沉默策略和情绪强度，而不是提供决策辅助。

### 有用理念：产品文档化

用途：

该项目通过产品说明和上下文术语文档统一团队理解。开放源项目长期维护尤其需要这种文档。

局限性：

文档本身不能替代架构边界。产品文档需要与代码模块和测试策略对应。

建议：

采纳。我们应长期维护产品愿景、非目标范围、架构决策记录和安全边界文档。

## sorena-ai/LeagueAiCoach

仓库地址：

https://github.com/sorena-ai/LeagueAiCoach

### 有用理念：结构化游戏状态报告

用途：

该项目先把游戏数据处理成结构化报告，再交给模型。这可以减少模型直接处理杂乱数据带来的幻觉。

局限性：

它的目标是 AI 教练，会回答玩家问题并给出建议。这与我们的解说员定位不同。

建议：

采纳管线思路，替换产品目标。我们的 `Game State Engine` 应输出结构化状态解释，供 `Narrative Director` 和 `Prompt Builder` 使用，而不是生成建议。

### 有用理念：来源优先级

用途：

该项目在提示词中定义了信息来源层级，告诉模型哪些信息更可信。这对防止模型幻觉很有帮助。

局限性：

它包含战略 playbook 和英雄指导内容，容易推动系统变成教练。

建议：

改进采纳。我们的来源层级应是：合法可见事实、结构化事件、游戏状态解释、叙事决策、风格约束。战略建议不应进入实时解说提示词。

### 有用理念：模型供应商抽象

用途：

可切换模型供应商能降低长期依赖风险。

局限性：

不同模型在延迟、成本、隐私和安全约束遵循能力上差异很大。

建议：

采纳。LLM 和 TTS 都应有 provider 抽象，但必须通过 Prompt Builder 和输出安全边界统一约束。

### 有用理念：会话生命周期

用途：

会话可以保存一局游戏内的上下文和历史输出，避免解说割裂。

局限性：

参考项目是问答型 session，不是连续实时解说 session。

建议：

改进采纳。我们需要的是 `MatchNarrativeSession` 概念，用于保存近期事件、叙事焦点、情绪节奏和 TTS 状态。

## johnnyinlee/lol-client-mcp

仓库地址：

https://github.com/johnnyinlee/lol-client-mcp

### 有用理念：Live Client API 薄适配层

用途：

该项目把 Riot Live Client API 封装成清晰工具，并处理连接、超时和错误。这种薄适配层对我们的 Riot Adapter 有参考价值。

局限性：

MCP 更适合给通用 AI 工具调用，不适合作为我们实时运行时的核心架构。该项目也不包含可见性过滤、状态融合、事件检测或叙事决策。

建议：

采纳薄适配理念，不采用 MCP 作为核心运行时。我们应实现自己的 Riot Adapter，并输出严格白名单数据结构。

### 有用理念：错误处理标准化

用途：

连接失败、游戏未开始、超时等状态需要被清晰表达，否则下游模块会误判。

局限性：

简单错误码不足以描述实时系统中的部分失败，例如 OBS 可用但 API 不可用、视觉置信度下降或 TTS 过载。

建议：

改进采纳。所有 Adapter 都应输出标准化健康状态和降级状态。

## 不应采纳的方向

以下方向不适合本项目：

- AI 教练。
- 操作建议。
- 自动接受、自动选人、自动禁用、自动符文。
- 聊天自动化。
- 战绩侦察和弱点识别。
- 基于隐藏信息的推断。
- 把 LLM 作为事实判断层。
- 把回放和审计日志塞进 MVP。

## 综合建议

我们应从参考仓库中借鉴以下理念：

- 数据采集与数据解释分离。
- 原始事实与下游摘要分离。
- 桌面端分层架构。
- 本地优先和 provider 抽象。
- 结构化状态报告。
- 会话生命周期。
- 薄 Adapter 和标准化错误处理。

但我们的核心架构必须是自己的：

- Event Detection 描述事实。
- Game State Engine 解释意义。
- Narrative Director 控制叙事。
- Prompt Builder 约束 LLM。
- LLM 只负责表达。
- TTS 负责实时语音输出。

这条链路服务于 AI 电竞解说员，而不是 AI 教练或作弊工具。
